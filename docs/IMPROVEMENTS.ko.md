# harnessay 개선 조사 — 2026-09-28

현재 코드, 저장된 실제 호출 24회, 기존 전체 리포트, 공개 도구의 공식 문서를 조사했습니다.
새 모델 호출이나 제품 기능 변경은 하지 않았습니다. 앞선 실험 보고서의 환경 관련 해석은 정정했습니다.

**우선순위는 실제 사용량을 빠짐없이 측정하고, 반복 행동의 근거를 구분하고,
작은 개선안 하나씩 효과를 검증하는 것입니다.** 일반적인 절약 지침을 늘리는 접근은 이번 실험으로 지지되지 않습니다.

## 1. 실제 입력·추론 사용량부터 보존

확인된 사실: `_tokens`는 `input_tokens`와 `reasoning_output_tokens`를 검증하지만,
Claude/Codex 이벤트로 변환할 때 입력 토큰을 보존하지 않습니다. Codex 추론 토큰도 사라집니다.
합성 기록의 입력 1,000, 캐시 600, 출력 40, 추론 30을 읽으면 출력 40과 캐시 600만 남았습니다.
실험 기록기 역시 원시 이벤트에 있는 추론 토큰을 요약에서 누락합니다.

- 위치: [파서](../skills/harnessay/harnessay.py), [비교 지표](../skills/harnessay/report_data.py), [실험 기록기](../experiments/benchmark.py).
- 최소 변경: 제공자별 의미를 유지한 입력·캐시·출력·추론 값과 해당 필드의 수집 여부를 보존합니다.
  필드가 없으면 0으로 단정하지 않습니다. Codex 캐시 입력과 추론 출력은 각각 해당 전체 값에 다시 더하지 않습니다.
  Claude 입력·캐시 의미는 별도로 정규화해야 합니다.
- 완료 기준: 같은 원시 기록의 값이 리포트까지 유지되고, 누락·명시적 0·부모/포크 중복·누적 카운터를 구분합니다.
- 사용자 가치: 출력 크기가 줄었어도 실제 입력 처리량이나 생성량이 늘어난 경우를 놓치지 않습니다.

모델·설정·실행 시간도 비교에 필요하지만, 기록에 없는 값을 추정해 채우면 안 됩니다.
기존 실행기는 모델·경과시간을 알고 있으므로 우선 그 값을 활용하고, 대화 전체 시간은 작업 수행 시간과 구분합니다.

## 2. 일반적인 절약 지침 대신 행동 하나를 바꾸는 제안

날짜 확인에서 guided 두 실행은 `test_harnessay.py` 실행이 임시 파일 문제로 실패한 뒤,
별도 Python 검증을 작성했습니다. 출력 토큰은 1,096/1,053, baseline은 418/342였습니다.
추론 토큰은 각각 47/73과 45/17이어서 출력 증가를 전부 추론 증가로 설명할 수 없습니다.
실제 명령 생성과 검사 범위도 함께 봐야 합니다.

원시 근거: 로컬 `benchmark-runs/2026-09-28-pilot/`의
`03-date-contract-guided.events.jsonl` 9·11행,
`16-date-contract-guided.events.jsonl` 13·16행.
명령별 시간이 없으므로 추가 지연을 모델 생성·도구 실행·대기 시간으로 분해할 수는 없습니다.

- 현재 안내의 문제 후보: “기존 검사 재사용”과 “필수 검사 보존”이 사실 확인 과제에서도 검사 범위를 넓힐 수 있습니다.
  이것은 관찰에 맞는 가설이며, 문구 하나의 인과효과를 입증한 것은 아닙니다.
- 최소 변경: 각 제안에 관측된 행동, 적용 조건, 바꿀 행동 하나, 확인 방법을 붙입니다.
  관측되지 않은 낭비에 범용 지침을 추천하지 않습니다.
- 예시: 사실 확인 과제에는 “관련 구현과 기존 검증으로 요청된 항목이 확인되면 종료한다.
  실행을 요구한 항목은 실행하고, 확인되지 않은 항목만 추가 검사한다.”를 시험합니다.
- 완료 기준: 정답·필수 실행을 유지하면서 불필요한 전체 검사나 재탐색이 줄어드는지 별도로 측정합니다.

개선된 과제에서는 더 구체적인 단서가 있습니다. 사용량 확인은 두 반복 모두
파일 목록 탐색을 생략하고 관련 심볼을 바로 검색해 셸 호출이 3회에서 2회로 줄었습니다.
한 반복은 출력 바이트가 오히려 조금 늘었는데도 빨랐습니다. 포크 확인도 각각 호출이
5→4회, 4→3회로 줄었습니다. 따라서 알려진 파일을 다시 찾는 왕복을 없애는 제안이 유망합니다.
다만 포크 실행에는 환경 실패도 있어 시간 차이 전체를 이 행동의 효과로 단정하지 않습니다.

반대로 집계 비교에서는 작은 모듈을 바로 읽은 baseline보다, 먼저 검색한 뒤 사실상
전체 모듈과 추가 자료까지 읽은 guided가 더 많은 출력을 반환했습니다.
따라서 “항상 검색부터”가 아니라 “파일을 알면 바로 해당 부분으로”가 더 적절한 검증 후보입니다.
근거: 같은 원시 기록 디렉터리의 13/14번 사용량 확인, 09/10번 집계 비교 실행.

## 3. ‘반복 횟수’와 ‘여러 세션에서 재사용할 가치’를 구분

현재 `skill_candidates`는 n-gram 등장 횟수만 셉니다. 단일 세션에서
`Bash:git → Bash:pytest`를 세 번 반복해도 스킬 후보가 생기는 것을 재현했습니다.
같은 실패를 세 번 복구한 것과 여러 작업에서 반복되는 유용한 절차가 구분되지 않습니다.
또 셸 명령은 첫 단어로 축약되어 `git status`와 `git commit`이 같은 `git`가 됩니다.

- 위치: [skill_candidates와 도구 시퀀스 집계](../skills/harnessay/harnessay.py).
- 최소 변경: 총 반복 수와 고유 세션 수를 함께 표시합니다. 한 세션에만 나타난 반복은
  스킬 승격 근거와 분리하고, 실패·복구 가능성이 있는 반복으로 검토하게 합니다.
  단순 명령에서 확실하게 읽을 수 있는 하위 명령만 구분하고 복잡한 셸은 미분류로 둡니다.
- 완료 기준: 같은 패턴이 1개 세션에 세 번 나온 경우와 3개 세션에 한 번씩 나온 경우가 구분됩니다.
  모르는 종료 상태를 성공이나 실패로 단정하지 않습니다.
- 사용자 가치: 설치할 필요가 없는 스킬과 불필요한 상시 지침이 늘어나는 것을 줄입니다.

## 4. Codex에서 무엇을 측정했는지 범위를 명시

기존 `report-all.json` 스냅샷의 도구 출력 173,300,514바이트 중
`exec`는 38.5%, `exec_command`는 35.9%였습니다. 이는 절약 가능한 비율이 아닙니다.
특히 일반 `exec` 내부의 하위 도구는 현재 분석하지 않으므로 38.5%를 상세 행동으로 설명할 수 없습니다.
구조화된 Read 통계도 Claude만 대상으로 합니다.

- 최소 변경: 도구 출력 집계·명령 분류·파일 재읽기 각각의 지원 범위를 리포트에 표시합니다.
  기록에 명시된 구조화된 명령/종료 상태부터 활용하고 임의 JavaScript나 셸 코드를 실행·추측 해석하지 않습니다.
- 재사용할 부분: 실험 기록기는 이미 `command_execution` 이벤트를 읽습니다.
  저장된 `codex exec --json` 기록 지원이 필요하면 이 작은 해석 로직을 공유할 수 있습니다.
  일반 rollout과 이벤트 형식은 구분해야 합니다.
- 완료 기준: ‘분석하지 못한 영역’과 ‘실제로 반복이 없는 영역’이 다르게 표시됩니다.

## 5. 개선안 검증을 제품의 핵심으로 연결

현재 제품 평가기는 최종 문자열 포함/정규식으로 판정하고, 실제 A/B 측정은 `experiments/`에 분리돼 있습니다.
새 평가 프레임워크를 만들기보다 기존 기록·채점·비교 기능을 작은 범위로 재사용하는 편이 낫습니다.

- 같은 모델·설정·소스·환경에서 개선안 하나만 바꿉니다.
- 정답과 요구된 실행을 먼저 판정하고, 입력·캐시·출력·시간을 따로 보여줍니다.
- 결과는 `개선 관찰 / 악화 관찰 / 불확실 / 실행 환경 오류`를 구분합니다.
  두 번 반복한 결과만으로 일반적인 절감률을 확정하지 않습니다.
- 실험 시작 전 임시 파일·검사 실행 가능 여부를 실제 사용할 환경에서 확인합니다.
  실패 원본과 재채점 기록은 보존합니다.
- 안내문을 조정한 과제는 개발용으로 취급합니다. 별도 과제·저장소에서 검증해야 일반화를 주장할 수 있습니다.

바로 다음 최소 실험은 기존 안내를 그대로 두고 날짜 확인만 양쪽 2회씩, 총 4회 실행하는 것입니다.
모델·지침·소스는 유지하고 환경을 쓰기 가능한 임시 스냅샷으로 바꿔, 임시 파일 오류 없이도
지연이 반복되는지 먼저 확인합니다. 이전 읽기 전용 실험을 새 조건의 대조군으로 섞지 않습니다.
그다음 필요할 때 날짜 확인과 사용량 확인 2개 과제에서 안내의 한 요소만 변경해 비교합니다.
이는 가설 선별용이며 제품 효과의 확증이 아닙니다. 이번 조사에서는 추가 호출하지 않았습니다.

## 시장에서 차별화할 방향

사용량·모델·캐시별 집계는 이미 [ccusage 공식 문서](https://ccusage.com/guide/codex/)에서 제공하는 영역입니다.
명령 출력 축약은 [RTK](https://github.com/rtk-ai/rtk)가 다루고 있으며,
해당 프로젝트도 셸 출력 감소와 전체 요금 감소를 구분합니다. 이 기능들을 크게 복제할 이유는 적습니다.

harnessay가 집중할 제품 가설은 **내 기록에서 문제를 찾고 → 수정할 행동을 제시하고 →
그 수정이 실제로 나아졌는지 확인하는 흐름**입니다. 경쟁 도구에 이 흐름이 전혀 없다는 주장은 아닙니다.
현재의 로컬 분석·원문 근거·비교 기능을 연결하는 방향이 기존 구현을 가장 많이 활용합니다.

공식 엔지니어링 자료도 필요한 맥락을 선별하는 도구 설계와 별도 평가 과제를 통한 검증을 권합니다.
이는 개선 방향의 근거이지 harnessay 효과의 증거는 아닙니다.
[Anthropic 도구 설계와 평가](https://www.anthropic.com/engineering/writing-tools-for-agents).
환경 자체가 평가에 영향을 준다는 점은 이번 임시 파일 오류와도 관련됩니다.
[Anthropic 평가 환경 연구](https://www.anthropic.com/engineering/infrastructure-noise).

실행 순서는 **사용량 보존 → 세션별 반복 구분 → 제안 한 개의 재검증**을 권합니다.
자동 지침 설치, 별도 DB, 실시간 대시보드, 새 출력 압축기는 현재 근거로 우선시하지 않습니다.
